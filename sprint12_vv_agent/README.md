# Sprint 12 — Agentic V&V Analyst

**Stack:** Python · LLM tool-use (Anthropic) · pytest

An autonomous certification analyst. It performs, end to end, the workflow a
V&V / DER engineer does by hand across a fleet: read the graded evidence from
Sprints 7–11, decide which analysis tools to run, run them, reason over the
results, and write a **certification findings report** — go/no-go decision,
each failure traced to a requirement, an evidence hash, an anomaly cluster,
and a recommendation, with the agent's full reasoning transcript appended as
an audit trail.

> Answers: *"Given a fleet's test evidence, which requirements fail, what is
> the root-cause pattern behind each, and is the fleet GO or NO-GO — produced
> the way a certification engineer would, but automatically?"*

It sits on top of Sprint 10's `polaris_fc` grading layer (13 verifiable
requirements over the battery pack, fixed-wing UAV, and landing multirotor),
so it reuses one source of truth for what "PASS" means and adds the
**autonomous investigation and reporting** layer on top.

---

## The two things a visitor should try

1. **Run it against the ratified catalog — a clean GO.**
   ```bash
   python scripts/run_agent.py          # basis: baseline
   ```
   Watch the agent survey the fleet, grade all 13 requirements, find nothing
   failing, and finalize **GO / GREEN**. The report's evidence manifest lists
   every requirement with its measured value and content hash.

2. **Tighten the acceptance basis and watch it find, diagnose, and block.**
   ```bash
   python scripts/run_agent.py --basis stress
   ```
   Same real measurements, stricter thresholds. The agent now surfaces two
   failures, drills into each (anomaly cluster → worst run → provenance),
   records a root-cause hypothesis and a recommendation, and — because one
   failure is a CRITICAL requirement — finalizes **NO-GO**. This is the whole
   findings loop running in front of you, every number traceable.

Add `--live` (with `pip install anthropic` and `ANTHROPIC_API_KEY`) to have an
actual language model drive the same tool layer instead of the deterministic
policy. **The numbers in the report are identical either way** — see below.

## What's modelled (and the important honesty notes)

**The agent has a closed, grounded action space.** Its only way to touch
evidence is a registry of nine typed tools (`grade_requirements`,
`inspect_anomaly_triage`, `get_evidence_provenance`, `record_finding`,
`finalize`, …), each with a JSON schema — the exact shape an LLM tool-use API
consumes. There is deliberately no "compute anything" tool. Every figure the
agent sees comes from Sprint 10's grading of the Sprint 7–11 artefacts.

**The language model cannot write a number into the report.** A finding is
only a `(requirement_id, root_cause, recommendation, disposition)` tuple. The
report generator re-binds every quantitative field — measured value, bound,
evidence hash, triage cluster — from the graded roll-up, *by requirement id*.
So the model (when enabled) chooses **which tool to call**, never **what the
data says**. Turning the LLM on or off cannot move a single figure; it can
only change the path taken to discover the findings. This is the
anti-hallucination guarantee, and it is exactly the property a V&V process
needs.

**The `stress` basis is a hypothetical, not a defect claim.** The measurements
are the real Sprint 7–11 numbers. `baseline` grades them against Sprint 10's
ratified catalog (the fleet passes). `stress` grades the *same* numbers
against deliberately tightened bounds (`FC-BAT-001` ≤ 0.05 SOC, `FC-LDG-001` ≤
0.03 m) to exercise the findings path. The report always names the basis in
force and prints the original catalog bound next to any tightened one. No
claim is made that the hardware failed its ratified requirements.

**No real hardware or flight data** — as in Sprints 7–11, all underlying
evidence is synthetic and generated by the sprints' own simulators.

## Architecture (one paragraph; full detail in `MODEL.md`)

A thin **ReAct loop** owns control — the step budget, the tool allow-list,
transcript keeping, and termination — and delegates every *decision* to a
swappable **Policy**. `DeterministicPolicy` encodes the fixed procedure a
methodical engineer follows (survey → grade → for each failure: triage,
provenance, disposition → finalize), so runs are byte-for-byte reproducible
with no network. `LLMPolicy` drives the identical tool layer through the
Anthropic tool-use API. The loop cannot tell them apart.

```
polaris_agent/
  tools.py    # ToolSpec registry + basis-aware grounded grading (the allow-list)
  agent.py    # ReAct loop, Policy interface, Deterministic + LLM policies
  report.py   # binds grounded numbers by requirement id -> findings report
scripts/
  run_agent.py  # CLI: --subsystem, --basis {baseline,stress}, --live
  verify.py     # reproduces every headline number below
tests/          # 18 tests: schemas, grounding, reproducibility, termination
reports/        # two curated sample outputs (baseline GO, stress NO-GO)
```

## Reproduce every number

```bash
python scripts/verify.py     # deterministic, no API key, exits non-zero on drift
python -m pytest -q          # 18 tests
```

`verify.py` runs the deterministic agent against the checked-in Sprint 7–11
artefacts and asserts the headline results:

- **baseline:** fleet **GREEN**, 0 findings, agent finalizes cleanly, no tool
  errors.
- **stress:** fleet **BLOCKED**, exactly `{FC-BAT-001, FC-LDG-001}` fail, **1
  blocking**, decision **NO-GO**.
- **grounding invariant:** `FC-BAT-001`'s measured value is identical under
  both bases (0.05461 SOC) — tightening a bound changes PASS/FAIL, never the
  measurement.
- **reproducibility:** the deterministic tool-call sequence is identical
  across independent runs (11 steps under stress).

See `reports/findings_stress.md` for a full sample findings report.
